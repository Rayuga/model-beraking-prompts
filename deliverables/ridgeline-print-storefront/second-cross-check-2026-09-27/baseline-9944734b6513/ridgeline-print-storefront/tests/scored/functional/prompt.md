## Evidence and isolation

- Perform the criteria in their listed order on one continuing database. Score each independently; after an ordinary failure, record it and continue. A failure is never evidence that another criterion passed or failed.
- Every numbered leg is required. Report concrete values, references, refusal behavior and fresh reads. Do not award a pass for an unperformed step or infer success from labels, a disabled button, a success toast or a response status alone.
- Start each new basket-based scenario by removing earlier unplaced lines. Do not consume a variant allocated to a later checkout scenario. Preliminary catalogue, basket, trade and postage criteria change no durable stock.
- The constraints gate has already purchased one Kiln A3. The reserved functional purchase chains are: historical comparison and mixed order use Long Field A3; mixed order also uses Kiln A3 and Two Weathers A3; address validation uses two further Kiln A3 purchases; monetary tampering uses Two Weathers A2; invalid/combined quantities use Nine Windows A3; stale multi-line checkout uses Harbour A3 with the currently observed Long Field A3 quantity; retries use Night Ferry A2; cancellation uses Night Ferry A3; concurrent buyers use Slack Water A3. Do not fail a later independent behavior merely because an earlier purchase never happened. ## Actual requests and fresh attempts

- Discover routes and payloads from the live UI and browser network activity. Record the actual successful method, path, headers and body. Use same-origin in-page browser requests for replays; never invent route names or demand a particular response shape.
- First establish each criterion's stated positive control with a successful operation. A negative probe must reach the real operation with otherwise valid data. Failure to reach an endpoint is not successful enforcement.
- Apart from explicit retry legs, each new checkout probe needs a fresh checkout-attempt identity. Follow the mechanism observed in the UI: prepare another checkout, use its observed attempt-creation exchange, or generate the same form of client attempt identity where that is what the application does. Never reuse an already completed attempt when testing stock, quantity or pricing. An idempotent old receipt would hide whether the new claim was validated.
- To alter a fresh checkout before it commits, capture/intercept that UI-generated request and change only the criterion's specified values, retaining the rest of its real shape. Browser request interception or a same-origin replay of the observed shape is valid. Do not require any particular field name for the attempt identity or variant identifier.
- Where the real request uses a list of lines, the duplicate-entry probe keeps that same list shape and duplicates only the selected variant. A unique-keyed representation cannot express duplicate variant entries; there use the required combined quantity instead. In both cases prove repeated UI additions merge, combined trade pricing is correct, and the combined overstock attempt is refused. This is an equivalent representation, not an exemption.
- After a refused write, re-read every affected stock value and existing receipt: there must be no successful new order and no change to those values. An HTTP error by itself does not pass; a non-4xx response with a real refusal and no mutation can pass. Safe rejection and authoritative repricing are both accepted only in the monetary-tampering criterion as described there.
- Concurrent-buying probes use different attempt identities. Exact retry probes preserve the original identity and body. A new purchase of the same basket is a different attempt. Keep these cases separate.
- The application is public. Do not add authentication, cross-user privacy, CSRF or tenant checks that the task never requested.

## State after restart

Only the final persistence criterion calls the verifier MCP tool restart_app, exactly once. It first creates its own placed and cancelled controls, records their requests, references and the current stock, then restarts the actual app process over the same database. Wait for the tool's success, open a fresh page, and perform the required lookups and replays. A browser reload is not a process restart. If the restart tool fails, report that evidence and fail the persistence criterion; do not claim a restart occurred.
