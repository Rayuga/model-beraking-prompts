## Scoring, failure and output limits

Separately scored outcomes can cite different observations from one action. A successful sibling is not evidence; a failed sibling cannot automatically suppress another result. Preserve the difference between an observed app defect and unavailable evaluator transport. A ledger kept inside one model call is useful execution bookkeeping, **not a durable checkpoint**. RewardKit does not save partial rows before that call completes, and a timeout still makes the full evaluation ungraded under the existing guard.

The current harness derives expected row count, names, IDs, weights and types from the TOML, so a legitimate row-count increase does not require a count-specific shell change. Binary weights remain ordinary positive weights; no scorer/schema workaround is needed. Keep concise final per-row actual-evidence reasoning and avoid emitting a second complete narrative ledger. Validate generated prompt and schema arguments after the final app-context substitution, since checking raw template size alone misses the criteria block and JSON example RewardKit appends.

9,000 seconds is 150 minutes. More output rows increase schema, output and bookkeeping, while fewer browser edits/Runs/tool round trips can save time. No unpaid static analysis establishes the net model wall time. Report the exact reduction in required operations and measured local workflow separately; do not claim hosted completion or a fixed timeout merely because a row count or nominal time sum fits.
