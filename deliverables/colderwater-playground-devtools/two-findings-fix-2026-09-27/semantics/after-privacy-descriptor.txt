3. Before judging any successful candidate response, distinguish an intended public role from private working-file delivery. A path actually used by the working playground as a browser asset or public product-data endpoint is allowed, even if its name matches a candidate. Establish that role from normal rendered UI and observed browser requests during ordinary use, without reading implementation text or the candidate response body. Record the observed public role; do not fail an asset because of its filename, MIME type or origin, and do not treat a file becoming reachable only because of this probe as evidence of an intended public role. A credible public-role ambiguity that the permitted browser observations cannot resolve is unavailable evidence under the incomplete-evaluation protocol, not a filename-based product failure.
4. For candidates without an established public role, accept a missing/denied HTTP response (for example 401, 403, 404 or 410), a no-content response, an equivalent clear refusal, or the actual working playground workspace with usable editor, preview and console. Redirects and normal SPA fallback are valid; use the final response and visible result. An established denial takes precedence over an attachment/download event on that denial response. A successful standalone file response or download without an established public role, denial or working-workspace fallback is an exposure outcome and fails this criterion. Do not read or classify implementation source, package fields, database bytes or probe response bodies, inspect downloaded contents or require a particular error wording or framework. If navigation is deliberately refused/closed, retry once and confirm the normal workspace still works; a reproducible refusal with a healthy control counts as denial. Tool crashes or unavailable browser observations use the incomplete-evaluation protocol instead.
