## Requirements that browser behavior cannot fully prove

`integration.md` requires TypeScript/React/Vite, Node/Express/better-sqlite3, SQLite, one server, `/app/server.js`, source/package/lockfile, `/app/public/index.html`, `/app/app.db` or `DB_PATH`, compiled frontend and no startup install or runtime dependence on `/assets`/`/instructions`. Build, harness, installer and image checks provide structural/runtime evidence. Browser Run/Save/restart behavior cannot prove the framework, database engine, exact internal files, lockfile provenance or every possible DB_PATH deployment. Do not label these fully browser-covered because a request succeeded.

Similarly, the promise not to evaluate user source on the server is a runtime/architecture boundary that browser behavior alone cannot exhaustively establish. The golden architecture review provides evidence; the scored criteria do not add hidden filesystem access or server exploitation probes to manufacture certainty. Time limits intentionally cover the supported source-written code, not arbitrary blocking native operations. Five refused dynamic families, literal loops, callbacks, parent reads/writes, CSS-installed handlers, fetch and Image are representative supported/boundary samples, not an exhaustive sandbox proof.

The new confidentiality check uses only browser HTTP responses from three published-runtime filenames. It never reads the filesystem, prints private bodies, analyzes application logic or extracts secrets/database rows. A completed 64 KiB prefix without a recognizable private signature satisfies that bounded probe even if a response is larger or its full type is unknown; report **no recognizable private content in the observed prefix**, not universal safety. Content beyond the cap, alternative paths and unusual encodings are not established. A transport/setup failure is different from a completed limited observation and cannot establish a pass. The classifier evidence includes positive leaks and benign controls precisely to avoid hidden status, MIME, filename or size requirements.

## Fairness, sequence and burden

All newly strengthened negative checks have a working control and bounded recovery. CSS's log-only listener avoids imposing snapshot semantics after a DOM-changing click. Auto-run measures the app's delay rather than prescribing milliseconds; actual edit timestamps distinguish missed automation setup from failure. Cancellation is assessed through state/output isolation without an unrequested supersession toast. Stop feedback remains required in the public note. Theme state preservation and switching remain functional, while aesthetic readability stays visual.

Every library chain owns its records and uses fresh/current revisions except when intentionally testing a stale request. Valid unrelated fields and positive controls prevent a broken route or wrong request shape from passing a negative. Existing gate records are preserved. Startup does not assume an empty library. Restart remains the final Functional criterion and establishes its own controls rather than borrowing a prior verdict.

The fixed Functional timeout is still 9000 seconds. One new criterion adds three bounded HTTP observations plus ordinary controls; existing criteria add a CSS click control and a measured edit sequence. These are real added judge actions. Local browser timings/proofs show feasibility, but full paid judging duration and reliability have not been measured. The exact weight crosswalk and functional-only score bounds are in `FUNCTIONAL_DELTA.md`; neither makes a model-score forecast.
