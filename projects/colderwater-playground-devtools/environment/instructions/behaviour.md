# Running and saving

When I press Run on a .js file, run it in a fresh, isolated preview page. A complete .html file becomes that preview page itself, and its inline scripts and handler attributes such as onclick should work. The browser can run whatever code it supports in the preview; the editor keeps exactly the code that I ran. Nothing from an earlier run, neither what it drew nor its variables, should leak into the next one. If my draft has a syntax error, tell me and leave the draft as it was. Show console output in the order it was written. Errors go to the same console with a useful message and a line number counted from one, both for a thrown error and for a Promise rejection that nothing handles; for an error inside a complete HTML file, count lines from the first line of that file. The message should be the text of the error or of the rejected value, not an empty object. Anything a run printed before it failed, was stopped or ran out of time stays in the console.

Keep the last run that worked as a last-good picture. If a later run throws, is stopped or goes over the five-second run budget, tell me why and put that picture back, including what I had typed into its fields and ordinary canvas drawing; it's fine if the restored picture is static. The budget covers the code itself and any timers or Promise callbacks still pending, until that run settles. Once it has settled, each time I interact with the preview, the callbacks from that interaction get a fresh five seconds of their own. After any of this, I should still be able to Run again.

Stop ends the current run straight away. Nothing left over from a stopped run, whether timers, intervals or Promise callbacks, should touch the preview or the console afterwards. The same goes when I press Run again while an older run is still waiting: the older run should never overwrite the newer preview or add to the console.

Save keeps a snippet's exact title, filename and code. A fresh page should read saved work from the running app, and my saved snippets and their history need to survive a full server restart. I sometimes have the same revision open in two tabs. If one tab saves first, a later Save from the other tab, still on the old revision, should be refused without changing the saved snippet or losing that tab's unsaved draft, and should tell me what happened.

When another tab saves, the library in my other open tabs should show it within about five seconds without a reload. That refresh shouldn't disturb what I'm doing: my draft, caret, scroll position and Undo history stay as they are, and the title and filename fields keep what I typed. If the snippet I have open got a newer revision somewhere else, let me know and keep my draft; don't load the newer revision over my work.

Looking at history is read-only and shows that snapshot's title, filename and code. Restoring an older snapshot makes it a new current revision of the same snippet and keeps all the history in between. Restoring from an old page must not overwrite a newer save. I keep the browser's network panel open while I debug, so please make saves and restores ordinary HTTP requests from the page that I can see there. My connection drops now and then, so if the same restore request arrives again after it already went through, for example because the reply got lost, it shouldn't create another revision.
